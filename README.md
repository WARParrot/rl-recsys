# RL для последовательных рекомендаций на Yambda

Эксперимент с GPT-2: сначала модель учится предсказывать следующий трек, затем дообучается с подкреплением, чтобы выбирать треки с более высокой ожидаемой долей прослушивания.

**В этом запуске RL не дал практически полезного улучшения.** Оценка модели награды выросла на 0,0763%, а NDCG@10 снизилась на 1,06% по точечной оценке. Простое переранжирование оказалось лучше выбранной RL-модели по обеим метрикам, хотя уверенного статистического превосходства мы не установили.

[Полный отчёт с настройками, таблицами и источниками](docs/reports/STUDY.md) · [Документация](docs/README.md)

## Что сделано

1. **Базовая модель (SFT).** GPT-2 обучена с нуля предсказывать следующий ID трека по истории пользователя.
2. **Модель награды (RM).** Отдельная сеть по истории и треку предсказывает долю прослушивания и приближённое время прослушивания.
3. **RL-дообучение.** REINFORCE оптимизирует оценку RM; KL-штраф удерживает политику рядом с исходной SFT. Проверены горизонты 1 и 5 шагов и три значения силы штрафа.
4. **Сравнение.** На одних и тех же данных оценены популярные треки, SFT, переранжирование по RM и шесть вариантов RL.

Для награды использовалась доля прослушивания: `min(played_ratio_pct / 100, 1)`. Вторая голова RM, предсказывающая время прослушивания, не прошла проверку качества, поэтому RL по этой награде не запускался.

При многошаговой генерации выбранный трек просто добавлялся в историю. Симулятор не моделирует, послушает ли его пользователь, пропустит или уйдёт из сервиса.

## Данные и настройки

Использован [Yambda-50M](https://huggingface.co/datasets/yandex/yambda): 1 000 пользователей, около 5,25 млн исходных событий. Из них удалены дубликаты и события с неоднозначным порядком внутри одной временной метки. Каталог — 20 000 самых частых треков обучающего периода; длина истории — до 64 треков.

Данные разделены по времени на обучение, калибровку, выбор RL-модели и тест. Каталог и статистики треков вычислены только на обучающем периоде. В истории каждого примера — только более ранние события пользователя. Веса на тесте не обновлялись.

| Настройка | Значение |
|---|---|
| GPT-2 | 4 слоя, 4 головы внимания, hidden size 128 |
| SFT | 5 000 шагов, batch 512, AdamW, learning rate `3e-4` |
| RM | Собственный GPT-2-энкодер истории и MLP с embedding трека; 3 000 шагов, batch 512, learning rate `3e-4` |
| RL | 1 000 шагов на вариант, learning rate `1e-5`, температура 1 |
| Горизонт / KL-штраф | `H ∈ {1, 5}`, `β ∈ {0.01, 0.1, 1}` |
| Seed обучения | 42 |

**Тестовый период уже просматривался в предыдущих итерациях.** Поэтому результаты ниже — разведочные, а не независимая проверка гипотез. Bootstrap по пользователям не заменяет повторное обучение с разными seed.

## Результаты

### Качество модели награды

На тестовых примерах с доступным целевым треком MAE для доли прослушивания:

| Модель | MAE ↓ |
|---|---:|
| Константа по обучающей выборке | 0,356982 |
| Среднее по треку | 0,347756 |
| RM с историей пользователя | **0,339790** |

У RM ошибка ниже среднего по треку на 2,29%, но 95%-интервал изменения — [−5,33%; +0,85%]. Уверенное преимущество не установлено; калибровка RM тоже оказалась недостаточной.

### Рекомендации до и после RL

Для NDCG и награды взяты **5 083 контекста / 733 пользователя**, у которых целевой трек входит в каталог (*eligible*). Это 50,83% из 10 000 тестовых контекстов. Recall считается по всем 10 000 контекстам / 837 пользователям, включая недоступные targets. Сначала метрики усредняются по примерам пользователя, затем — по пользователям.

| Модель | Ожидаемая оценка RM ↑ | NDCG@10 ↑ | Recall@10 ↑ |
|---|---:|---:|---:|
| Популярные треки | 0,729154 | 0,006310 | 0,008294 |
| SFT | 0,729139 | 0,044494 | 0,036971 |
| Переранжирование | **0,729961** | **0,045192** | **0,036971** |
| Выбранная RL, H=1, β=0,01 | 0,729696 | 0,044024 | 0,035750 |

RL-модель выбрана на отдельном периоде selection, а не по тестовой таблице: максимальная награда среди H=1-вариантов с NDCG не ниже 98% от SFT.

Изменения выбранной RL относительно SFT, с парным 95%-bootstrap-интервалом по пользователям:

- **Ожидаемая оценка RM:** +0,0763% [+0,0705%; +0,0823%].
- **NDCG@10:** −1,06% [−4,50%; +2,61%].
- **Recall@10:** −3,30% [−7,29%; +0,28%].

Прирост награды намного меньше принятого в исследовании порога +5%. Сохранение NDCG в пределах допуска −2% тоже не подтверждено. При этом интервал NDCG включает ноль — доказанного ухудшения нет.

Здесь награда — ожидание оценки RM по всему каталогу, `Σ π(a|s) × RM(s,a)`, а не реальный отклик пользователя и не средняя оценка top-10. Для переранжирования используется `log π_SFT + RM`, преобразованное в распределение через softmax. Точность суммирования не означает, что сама RM безошибочна.

### Как изменилось поведение

- Рекомендации стали немного более концентрированными: покрытие каталога снизилось с 29,535% до 28,760%, HHI вырос примерно на 15%. Коллапса к одному списку для всех пользователей не наблюдалось.
- Доля знакомых треков в top-10 почти не изменилась: 12,09% у SFT и 11,94% у RL.
- Средняя длительность рекомендованных треков немного снизилась: с 194,63 до 192,63 секунды. Этого недостаточно, чтобы уверенно объяснить рост награды предпочтением коротких треков.
- За пять синтетических шагов оценки RM росли даже при добавлении случайных или популярных треков. Другая модель-аудитор этот рост не повторяла. Это указывает на чувствительность к искусственной истории, но не доказывает специфичный для RL reward hacking.

## Выводы и ограничения

Для этого запуска усложнение обучения не окупилось: RL немного поднял собственную целевую функцию, но не показал практически значимого выигрыша. Простой rerank остаётся важным базовым сравнением.

Результат ограничен одним seed, повторно использованным тестом и сокращённым каталогом. RM обучалась на логах прослушиваний, без полного журнала показов и вероятностей выбора треков. Поэтому её оценки нельзя считать причинной оценкой новой рекомендательной политики. Отдельная модель-аудитор — тоже не истинная пользовательская награда.

Удержание здесь не измерялось. Для следующего шага можно предсказывать продолжение сессии или возвращение в заданном будущем окне, учитывая цензурирование и границы временных выборок. Офлайн можно проверить качество таких прогнозов; влияние рекомендаций на удержание потребует отдельного дизайна, например онлайн A/B-теста.

Отдельный запуск с completion-only RM также не прошёл проверку допуска и завершился только контрольными продолжениями SFT — **без нового RL**. [Результаты этого запуска](docs/reports/COMPLETION_RESULTS.md). Новый набор Experiment A реализован, но завершённый полный запуск не заявляется; с приведёнными выше результатами он не смешивается.

## Как повторить

### Установка и обучение

Нужны Python 3.11 и совместимый с PyTorch GPU. Команды выполняются из корня репозитория. Для повторения исторического эксперимента используется ревизия `68578e4`:

```bash
git clone https://github.com/WARParrot/rl-recsys.git
cd rl-recsys
git checkout 68578e4ae753214b506d146e04f8207686b3c852
python3.11 -m venv .venv
. .venv/bin/activate
python -m pip install --upgrade pip
# Выберите wheel под свой GPU и драйвер; cu128 — пример.
python -m pip install torch --index-url https://download.pytorch.org/whl/cu128
python -m pip install -e '.[test]'
python -m pytest -q
rl-recsys preflight --config configs/pilot.json --device cuda

rl-recsys download --config configs/pilot.json --output data/listens.parquet
rl-recsys prepare --config configs/pilot.json --input data/listens.parquet --output data/prepared
rl-recsys train --config configs/pilot.json --data data/prepared --run runs/reproduction-seed42
rl-recsys evaluate --data data/prepared --run runs/reproduction-seed42 > evaluation.json
```

Ревизия и SHA-256 датасета закреплены в конфигурации; используется новый каталог запуска. Проверка окружения не оценивает полное время работы и расход памяти. Лимиты исторической конфигурации — 36 часов обучения и 120 минут оценки, а не измеренная длительность. Исходный запуск выполнен на Windows с RTX 5060 Ti. Совпадение seed не гарантирует побитового совпадения на другом оборудовании.

На **текущей версии** репозитория в Windows исторический pilot запускается так:

```bat
run_windows.bat pilot
```

Без аргументов `run_windows.bat` запускает другой, новый набор Experiment A. [Его описание](docs/research/REWARD_DESIGN.md).
